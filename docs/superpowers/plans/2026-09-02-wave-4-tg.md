# Balance Pass Wave 4 — TG Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Land TG's whole share of the 2026-09-02 balance pass — five new cards
and sixteen updated ones — with every new card's behaviour wired in the same
wave, so `KNOWN_GAPS` never reopens.

**Architecture:** Everything happens in one effect module and one seed file.
`shared/effects/tgEffects.ts` gains **two rewrites** (`horrorBattle`'s
aggressor gate, `duelEffect`'s draw-on-kill continuation) and **six new
registrations** — `spiteOnPlay` and `agonyOnPlay` sharing one factory under
two ids, plus `loathingOnPlay`, `wonderOnPlay`, `repurposeEffect` and
`spawnAudaciousEffect`. The remaining thirteen cards are pure seed data. No
new engine mechanic, no new meta key, no new keyword, and no frontend change:
every targeting mode and dialog these cards need already ships.

**Tech Stack:** TypeScript (strict), Vitest, React 19 + Tailwind v4, TanStack
Query v5. Pure game rules live in `shared/` and are imported by both the
frontend and the Deno edge functions.

**Spec:** [docs/superpowers/specs/2026-09-02-balance-pass-design.md](../specs/2026-09-02-balance-pass-design.md)
— read §6.4 in full, plus §1.1, §2.3, §3 (R-6, R-7), §5 and §7 before
starting. This plan implements §6.4 in full.

## Global Constraints

- **Shell is PowerShell.** No `&&` chaining — use `;` or separate calls.
- **Every commit touching `shared/` must include `npm run functions:sync` output.**
  `supabase/seed/functionSharedSync.test.ts` fails otherwise.
- **Relative imports inside `shared/` require the `.ts` extension** — Deno runs
  these files verbatim inside edge functions.
- **Run the full suite with `npx vitest run`. NEVER pass `--root`** — it

  same commit**, or `supabase/seed/seedDataSync.test.ts` fails.
- **A card's `name` is immutable.** `transform.ts` derives each row's uuid from
  `card:<faction>:<name>`; renaming mints a new id and orphans every deck
  holding the old one. This wave renames nothing — the five new names
  (`Mania`, `Spawn Audacious`, `Agony`, `Wonder`, `Repurpose`) are chosen once
  here and are frozen from the moment they are seeded.

  before any card names it fails **G4** (`effectCoverage.test.ts`); seeding a
  card before its effect exists fails **G1** and would need a `KNOWN_GAPS`
  entry, which spec §1.1 forbids for this pass. Every task below therefore
  ships test → implementation → seed row → `seed:build` together.
- **`KNOWN_GAPS` stays empty and its `toHaveLength(0)` literal never moves.**
  If a task finds itself wanting an entry, the task has been split wrongly.
- **`DELIBERATE_ORPHANS` is unchanged.** This wave orphans nothing: no TG card
  loses a meta key. Spite and Loathing GAIN one, Duel and Horror keep theirs.
- **Every effect gets its own registry id (spec R-6).** Agony and Spite share
  one factory and two registrations. `spawnAudaciousEffect` never reuses
  `spawnBuccaneerEffect`. A reused name rebinds another card's behaviour
  mid-game for every in-flight game at once (Kraken/Paddlegun).
- **Keywords live in TWO files.** `shared/gameSettings.ts` **and**
  `supabase/seed/source/gameSettings.js` are separate hand-maintained maps, and
  adding a keyword to only one writes `null` into jsonb with every guard green

  keyword it writes (`robotic`, `upkeepRequired`, `blocker`, `fragile`,

  guard that would catch it anyway is
  `supabase/seed/tgFaction.test.ts`, `describe('the seed vocabulary matches shared/gameSettings')`.
- **Public `state.log` must never name a card in a hidden hand.** Duel's new
  draw logs the kill, never the card drawn.
- Report the suite's **before→after passing count** at the end of the wave, not

**The change, precisely.** Today:

```ts
registerEffect('horrorBattle', ({ game, actor, ctx, card, battle }) => {
  if (!battle || battle.phase !== 'resolve' || !battle.survived) return true
  const found = findVehicle(game.state, card.instanceId)
  // Destroyed hulls are still in `participants` when the resolve dispatch
  // runs, so this is reachable rather than defensive.
  if (!found || found.side !== actor) return true
```

The new text is *"Whenever a horror participates in an **offensive** fleet
battle"*. Two edits, and **the second is the one that is easy to miss**:

1. `!battle.survived` → an aggressor gate. "Offensive" is
   `!battle.isDefender`. That is exactly what
   `dispatchBattleResolve` computes: `isDefender: side !== aggressor`
   (`shared/engine/battleTriggers.ts:278`), so the attacking side of any
   battle — declared, forced, or a Duel — reads `isDefender: false`.
   `wfEffects.ts:111` already gates the same way.
2. **`findVehicle` must stop being the only route to the zone.** Removing the
   survival gate alone changes nothing for a dead Horror: the destruction
   branch has already spliced it out of `zone.cards` by the time the resolve
   dispatch runs, so `findVehicle` returns `null` and the effect still returns
   early. The zone falls back to `battle.zoneId`, and the copy is built from
   `card` — the payload's `card` **is** the participant's full
   `ZoneCardEntry` (`fire()`, `battleTriggers.ts:69-81`), granted keywords and
   all.

   The fallback is exact rather than approximate, and only because of the
   aggressor gate: every hull on the aggressor's side of a battle is in the
   battle's own zone. `ATTACK_ENEMY_FLEET` validates attackers against
   `zone.cards[actor]`; `joinBattle` requires the same for an on-board id; and
   a cross-zone Duel sets `zoneId: mine.zone.id` — the *aggressor's* hull's
   zone (`tgEffects.ts`, `resolveDuel`). A defending Horror could be the away
   hull, and it is precisely the case the new gate excludes.

**Two traps, both load-bearing.**

1. **The router must branch on `continuation` FIRST.** It currently reads:

   ```ts
   registerEffect(DUEL, (payload) => {
     const stashed = payload.pending?.data?.friendlyId
     if (typeof stashed === 'string') return duelHop2(stashed)(payload)
     return duelHop1(payload)
   })
   ```

   A continuation re-entry carries neither `resolution` nor `pending`, so it
   would fall through to `duelHop1` and **offer a brand-new duel** off the back
   of the battle that just resolved. `dwgWatersEffect` and `trebuchetEffect`

2. **The kill test comes off `battle.casualties`, not off the board.** By
   continuation time the enemy hull is out of `zone.cards`, `activeBattle` is
   null and `state.destroyed` holds a bare snapshot with no `instanceId`.
   `casualties` is the only carrier of "which hulls died in this battle"
   (`engineTypes.ts`, `BattleContext.casualties`), and
   `DECIDE_BATTLE_REPORT` hands the continuation the same list the resolve
   triggers saw.

// Entry (c): the duel's battle has resolved. activeBattle is already null —
// DECIDE_BATTLE_REPORT nulls it before firing the continuation — so the
// outcome arrives on payload.battle, the SAME BattleContext the resolve
// triggers were handed, scoped to the Duel card itself.

// of zone.cards and state.destroyed holds a bare snapshot with no instanceId,
// so no board read can answer "did the hull I named die?".
//
// ⚠ A hull revived by Iron Cordon in the same DECIDE_BATTLE_REPORT is still
// in `casualties`, so the draw stands. That is DP2 departure 7's existing
// rule — a revive undoes the discard, not what already fired — rather than a
// new ruling.
function duelAftermath(payload: EffectPayload): boolean {
  const { game, actor, card, continuation, battle } = payload
  const enemyId = continuation?.data?.enemyId
  if (typeof enemyId !== 'string') return false
  const died = (battle?.casualties ?? []).some(
    (c) => c.side === otherSide(actor) && c.entry.instanceId === enemyId,

  // hand. grant() resyncs state.counts for us.
  game.state.log.push(`${card.name} claims its kill — a card is drawn`)
  return grant({ draw: 1 })(payload)
}

// "When played, grant an enemy vehicle FRAGILE." Printed identically on TG
// Spite and TG Agony (2026-09-02 spec §6.4), so the behaviour is one factory —
// and TWO registrations, under two names.
//
// ⚠ `effect` is a PARAMETER rather than a constant closed over inside, and
// that is the whole safety of sharing the shape. `choice` never sees the name
// registerEffect files it under, so each registration must hand in its own;
// passing the other card's name compiles, passes any test that calls the
// effect directly, and fails only when a live player answers the dialog.
// Reusing one id for both is the Kraken/Paddlegun collision (spec R-6): the
// name is frozen into dealt game state, the implementation is redeployed for
// every game at once.
//
// ⚠ NOT a grantKeywords composition, and composing it would fail SILENTLY —
// grantKeywords reads payload.targetInstanceId, which PLAY_CARD_TO_ZONE never
// sets for an onPlayEffect and RESOLVE_PENDING_EFFECT never sets at all. This
// is hysteriaOnPlay's shape, and its comment is the long version.
//
// `zoneId: null` scopes the offer to the WHOLE board: the text says "an enemy
// vehicle", with no zone qualifier. On-field vehicles are already public, so
// pendingEffect.options leaks nothing.
function fragileGrant(effect: string, prompt: string): EffectFn {
  return choice({
    effect,
    prompt,
    options: ({ game, actor }) => enemyVehicleOptions(game, actor, null),
    resolve: ({ game, actor }, choiceId) => {
      // No enemy vehicle anywhere: choice() resolves straight through with
      // null, and that is a success — the hull still deploys.
      if (choiceId === null) return true
      // Re-checked against the board rather than trusted from the first entry:
      // the hull can be gone by the time the dialog is answered.
      const found = findVehicle(game.state, choiceId)
      if (!found || found.side !== otherSide(actor)) return false
      // Idempotent, matching grantKeywords: a keyword already carried is not
      // duplicated.
      if (!found.entry.keywords.includes(KEYWORDS.FRAGILE)) {
        found.entry.keywords = [...found.entry.keywords, KEYWORDS.FRAGILE]
      }
      game.state.log.push(`${found.entry.name} is made Fragile`)
      return true
    },
  })
}

**Ruling TG-1 — "its cost" is `effectiveMaterialCostOf`, not
`effectiveCostInGame`.** Stated here because the two are one import apart and
the difference is invisible in review.

`effectiveCostInGame` (`placement.ts:250`) is **play-time only** by
construction: it sums `costModifier`, the stored `costDelta` stamp, and the
active `resourceSurge` delta, all of which are mechanics about *paying for a
card out of hand*. Repurpose's target is a hull that is already deployed and
already paid for. Reading `resourceSurge` against the current material pool for
a board hull is meaningless; reading a spent `costDelta` stamp is worse than
meaningless. Spec ruling U-1 makes exactly this call for upkeep, in the same
words: "`effectiveMaterialCostOf`, never `effectiveCostInGame`. The latter is
play-time-only … and must not reach a recurring charge."

`effectiveMaterialCostOf` (`costs.ts:19`) is what every other on-board
valuation already uses: `repairCostOf` (`battleResolve.ts:21`),
`baseDamageFrom` (`baseAttack.ts:33`), `upkeepOwedBy` (`costs.ts:51`) and
Boarding Party's own comparison (`heroPowers.ts:35`). It applies Half-Cost and
nothing else, which is the price the owner actually paid.

The apparent counter-example is `sapphireEffect` (`lhEffects.ts:60`), which
*does* use `effectiveCostInGame` — and correctly: it refunds the cost of the
card **being played, from hand, this instant**. That is the one situation the
play-time authority is for.

**Ruling TG-2 — "destroy it" fires the death trigger.** Spec R-7 rules the
mirror case for WF Sub Strike: "remove it from play" is not "destroy it", so
`onDeathEffect` does **not** dispatch. Repurpose prints "destroy it", so it
does. Mechanically that is `sacrificeEntry` (which routes through
`discardCard`, the single exit out of play, so a captured hull still goes home)
followed by `fireDeathEffect` — the order `battleResolve` itself uses, and the
order `nostalgiaOnDeath` requires, because `returnToHand` pulls the snapshot
back out of the discard `sacrificeEntry` just filed.

This is live rather than theoretical: TG Jealousy draws on death and TG
Nostalgia returns itself to hand, so a TG player meets it in their own deck.

**Ownership is validated here, not by the handler.**
`PLAY_CARD_TARGETING_CARD_ON_FIELD` (`placement.ts:467-476`) checks only that
the target is *on the field* — never whose it is. That is ruling E-5's shape,
and the Factories already carry the same own-side check for the same reason.
Without it, Repurpose scraps an enemy hull and pays its owner's opponent for
it.

// "Target a friendly TG vehicle. destroy it. gain resources this turn equal to
// its cost."
//
// ⚠ Ruling TG-1 — "its cost" is effectiveMaterialCostOf, NEVER
// effectiveCostInGame. The latter sums costModifier, the stored costDelta
// stamp and the active resourceSurge delta: all three are about PAYING for a
// card out of hand, and this target is a hull already deployed and already
// paid for. Spec ruling U-1 makes the identical call for upkeep, and
// repairCostOf, baseDamageFrom, upkeepOwedBy and Boarding Party all read the
// same authority for the same reason. sapphireEffect's use of the play-time
// one is not a counter-example: it refunds the card being played, from hand,
// at that instant.
//
// ⚠ Ruling TG-2 — "destroy it" FIRES onDeathEffect. Spec R-7 rules the mirror
// for WF Sub Strike ("remove it from play" does not), and the two phrasings
// are one line apart here. sacrificeEntry alone would be the removal case;
// the fireDeathEffect below is what makes this the destruction case. The
// ORDER matters as well as the call: nostalgiaOnDeath pulls its snapshot back
// out of the discard that sacrificeEntry just filed, which is the same
// sequence battleResolve uses.
//
// ⚠ Ownership and faction are validated HERE because the handler does not:
// PLAY_CARD_TARGETING_CARD_ON_FIELD checks only that the target is on the
// field (ruling E-5, the same gap both Factories close by hand).
//
// "this turn" needs no mechanic. endTurn ASSIGNS the material pool from the
// turn number rather than incrementing it, so every material gain in the game
// already expires with the turn.
//
// Balance, recorded rather than fixed: Spawn Audacious mints a Half-Cost
// Audacious for 40k, and Repurpose converts that hull to 330k for 1cp. Two
// cards and a CP for a ~290k swing is a real loop. Both numbers are the
// spec's (§6.4) and neither card's text admits a guard against it.
registerEffect('repurposeEffect', ({ game, actor, ctx, card, targetInstanceId }) => {
  if (typeof targetInstanceId !== 'string') return false
  const found = findVehicle(game.state, targetInstanceId)
  if (!found || found.side !== actor) return false
  if (found.entry.faction !== FACTIONS.TG) return false
  // Read before the hull leaves the board, so the payout cannot depend on
  // ordering.
  const entry = found.entry
  const value = effectiveMaterialCostOf(entry)
  if (!sacrificeEntry(game, actor, targetInstanceId, found.zone.id)) return false
  fireDeathEffect(game, ctx, actor, entry)
  game.state.resources[actor].materials += value
  game.state.log.push(`${card.name} scraps ${entry.name} for ${value} materials`)
  return true
})

## Deploy note

Merging to `main` deploys automatically via the Supabase GitHub integration,
which runs migrate → seed → deploy. This wave adds **no migration** — every
change is card data in an existing jsonb/int column plus effect code.

**Merge order.** `supabase/seed/seed_data.sql` is generated, so every branch in
this pass rewrites it and every rebase conflicts there. The resolution is
always the same and is never a hand-edit: take either side, run
`npm run seed:build`, commit. `seedDataSync.test.ts` is what proves the result
correct (spec §1).

**Deploy from a branch that is up to date with `main`,** so a production fix
already on `main` is not regressed. `game-action` is the only function this
wave changes. If a manual deploy is needed, use
`npm run functions:deploy -- game-action` — **never** the
`deploy_edge_function` MCP tool and never a subagent, both of which truncate
the payload and delete every file they omit. Afterwards verify the deployed
version incremented **by content, not file count**: a deploy legitimately reads
back with fewer modules, because type-only imports are erased in transpilation.

⚠ **Nothing here breaks an in-flight game.** Cost and keyword changes apply to
newly dealt snapshots only, and every effect this wave changes keeps its
registry name, so the 28 live games keep resolving. The one visible mid-game
change is `horrorBattle`'s: an in-flight Horror starts splitting on offensive
battles it does not survive, and stops splitting on defensive ones, the moment
`game-action` redeploys. That is code, and code does retrofit live games
(spec §9.2 of the 2026-08-27 spec) — it is the intended behaviour, but say so
in the PR rather than letting a player discover it.
