# Balance Pass Wave 1 — DWG Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Land DWG's six updated cards — data *and* effects together, so no card
ships text the engine cannot honour.

**Architecture:** Two effect edits and four data edits. Marauder pays for its
capture discount with 15k of printed cost and loses the discount entirely,
which retires `MARAUDER_DISCOUNT`. Plunderer's raid gains a price: the card it
takes arrives stamped with a `+20_000` `costDelta`, the same per-instance
mechanism Marauder's discount used in the other direction. The remaining four
cards are keywords and numbers, pinned by a new per-faction balance guard.

**Tech Stack:** TypeScript (strict), Vitest, React 19 + Tailwind v4, TanStack
Query v5. Pure game rules live in `shared/` and are imported by both the
frontend and the Deno edge functions.

**Spec:** [docs/superpowers/specs/2026-09-02-balance-pass-design.md](../specs/2026-09-02-balance-pass-design.md)
— read §6.1 before starting, and §3 (R-8), §5, §7.1 and §7.2, all of which bind
this wave. This plan implements §6.1 in full.

**Prerequisite: Wave 0 must be merged, and this branch rebased onto it.** Wave 0
creates `supabase/seed/balance/dwg.balance.test.ts` as a placeholder; Task 3
replaces its body. Starting before Wave 0 lands means creating that directory
here, which puts two branches back into one file — the single thing §2.3 exists
to prevent.

## Global Constraints

- **Shell is PowerShell.** No `&&` chaining — use `;` or separate calls.
- **Every commit touching `shared/` must include `npm run functions:sync` output.**
  `supabase/seed/functionSharedSync.test.ts` fails otherwise.
- **Relative imports inside `shared/` require the `.ts` extension** — Deno runs
  these files verbatim inside edge functions.
- **Run the full suite with `npx vitest run`. NEVER pass `--root`** — it
  silently runs 0 tests.
- **Any edit to `supabase/seed/source/**` requires `npm run seed:build` in the
  same commit**, or `supabase/seed/seedDataSync.test.ts` fails.
- **A card's `name` is immutable.** `transform.ts` derives each row's uuid from
  `card:<faction>:<name>`; renaming mints a new id and orphans every deck
  holding the old one. This wave renames nothing.
- **An effect keeps its registry id.** `marauderOnPlay` and `plundererRaid` are
  strings frozen into `games.state` at deal time. This wave edits the two
  implementations behind those names and **renames neither** — a new id would
  orphan the old one, and reusing an id for another card is the
  Kraken/Paddlegun collision (`docs/claude/card-effects.md`, workflow rule 2).
- **A keyword must exist in BOTH vocabularies.** `supabase/seed/source/*.js`
  import `supabase/seed/source/gameSettings.js`, a second hand-maintained
  `KEYWORDS` map. This wave adds no new keyword — `subScreen` and `fragile` are
  already in both — but check rather than assume.
- **This wave retires nothing.** It does not touch `DELIBERATE_ORPHANS`, and
  `KNOWN_GAPS` must still be **empty** at close (spec §1.1).
- **Public `state.log` must never name a card in a hidden hand.** Both effects
  edited here put a card into a hidden hand; neither may start naming it.
- Report the suite's **before→after passing count** at the end of the wave, not
  "tests pass".

### Task 2: Plunderer's raid arrives with a 20k surcharge

**Files:**
- Modify: `shared/effects/dwgEffects.ts:44-59` (the effect)

- Test: `shared/effects/dwgEffects.test.ts` — `describe('plundererRaid')`, and

**Interfaces:**
- Consumes: nothing from Task 1 — the two effects are independent, and
  `PLUNDERER_CAPTURE_SURCHARGE` is a new constant, not a repurposed one.
- Produces: `export const PLUNDERER_CAPTURE_SURCHARGE = 20_000` from
  `shared/gameSettings.ts`. Task 3 prints the matching clause on the card.

**Where the surcharge lands.** `meta.costDelta` is a stored per-instance
discount summed into `effectiveCostInGame` (`shared/engine/placement.ts:253`),
which clamps the result at `Math.max(0, …)`. A **positive** delta is new — every
existing one is a discount — but it needs no engine change: it raises the price,
and the clamp only ever protects the floor. It never reaches
`effectiveMaterialCostOf`, so the surcharge does not inflate the raided card's
repair cost or its in-battle resource value; it is a play price only. And
`costDelta` is stripped from every card leaving play, so a raided card that is
played, dies and is somehow reacquired does not carry a stacked surcharge.

### Task 4: FRAGILE printed, SCRAPPY granted — pin what one Buccaneer actually carries

**Files:**
- Modify: `shared/effects/dwgEffects.test.ts` (one import, one new `describe`)

**Interfaces:**
- Consumes: Task 3's seeded `DWG:Buccaneer` keywords (`['fragile']`), pinned in
  `dwg.balance.test.ts`. This task pins what the *effect* does with them.
- Produces: nothing consumed later. **No production code changes in this task.**

**⚠ Investigated, and spec §6.1's premise does not hold.** §6.1 says
"`spawnBuccaneerEffect` mints Buccaneer hulls with `SCRAPPY` per its text, and
Buccaneer now prints `FRAGILE`… Both on one hull is legal… but assert it." The
first half is right; the conclusion is not. The effect does **not** merge the
granted keyword into the printed ones — it **replaces** the array:

```ts
  const entry: ZoneCardEntry = {
    ...buccaneer, instanceId: ctx.newId(), keywords: [KEYWORDS.SCRAPPY],
    playedOnTurn: game.turnNumber, movedOnTurn: null, activatedOnTurn: null,
  }
```

The spread puts `buccaneer.keywords` in and the explicit `keywords:` overwrites
it wholesale. So after Task 3 there are two Buccaneers with different keyword
sets: one **played** from hand is `['fragile']`, one **spawned** is
`['scrappy']`, and the pair never coexists on a hull. That is invisible today
only because Buccaneer prints `[]`.

This is deliberate rather than accidental: `describe('spawnBuccaneerEffect')`'s
first test already feeds the effect a catalog Buccaneer carrying
`'someOtherKeyword'` and asserts the minted hull is `[KEYWORDS.SCRAPPY]` alone.
Note also that `spawnBuccaneerEffect` hand-rolls its entry rather than calling
`mintHull` (`shared/effects/primitives.ts:211`), which **does** merge:
`[...snapshot.keywords, ...keywords.filter((k) => !snapshot.keywords.includes(k))]`.

**This wave pins that behaviour and does not change it.** §6.1 authorises no
effect edit to `spawnBuccaneerEffect`, and converting it to a merge is a balance
change rather than a correction: `autoRepairIds` checks FRAGILE before SCRAPPY,
so a merged hull would never auto-repair and the granted SCRAPPY — the whole
point of a 225k ability — would be inert. Raise it in the PR as a question for
the spec owner; do not decide it here. The close-out names it as unfinished.

The engine rule §6.1 worries about is already covered end to end by
`shared/engine/battleResolve.test.ts:385` ("never auto-repairs a Fragile
vehicle", with `keywords: ['scrappy', 'fragile']`). What is **not** covered is
which of the two shapes each Buccaneer gets, which is what this task adds.

```ts
// Buccaneer prints FRAGILE from the 2026-09-02 pass, and Spawn Buccaneer's text
// grants SCRAPPY. Spec §6.1 asks for the combination to be asserted because it
// reads like a contradiction. On a spawned hull it never actually arises:
// spawnBuccaneerEffect REPLACES the printed keyword array rather than merging
// into it (unlike mintHull), so a spawned Buccaneer is Scrappy-only while a
// played one is Fragile-only. Both shapes are pinned here with the repair
// verdict each earns — and so is the verdict for a combined hull, so the answer
// is on record if the two ever are merged.
//
// The seeded value these fixtures mirror is pinned in
// supabase/seed/balance/dwg.balance.test.ts; nothing under shared/ may read the
// seed, so the two files close the loop between them.
describe('Buccaneer: FRAGILE printed, SCRAPPY granted', () => {
  const seededBuccaneer = () =>
    snap({ name: 'Buccaneer', vehicleType: 'airship', keywords: [KEYWORDS.FRAGILE] })

  function spawned() {
    const game = makeGame()
    const ctx = makeCtx({ catalog: [seededBuccaneer()] })
    const ok = effectFor('spawnBuccaneerEffect')!({
      game, actor: 'a', card: inst(), ctx, targetZoneId: 1,
    })
    expect(ok).toBe(true)
    return game.state.zones[0].cards.a[0]
  }

  it('mints a Scrappy hull that does not inherit the printed Fragile', () => {
    // toEqual, not toContain: a merge would read ['fragile', 'scrappy'] and
    // satisfy a containment check while reversing the hull's repair behaviour.
    expect(spawned().keywords).toEqual([KEYWORDS.SCRAPPY])
  })

  it('auto-repairs the spawned hull in the band, and never the played one', () => {
    const hull = spawned()
    const played = zoneEntry({ name: 'Buccaneer', keywords: [KEYWORDS.FRAGILE] })
    const results = { [hull.instanceId]: 85, [played.instanceId]: 85 }
    const roster = [
      { entry: hull, side: 'a' as const },
      { entry: played, side: 'a' as const },
    ]
    expect(autoRepairIds(roster, results)).toEqual([hull.instanceId])
  })

  it('repairs neither, if the two keywords ever do land on one hull', () => {
    // autoRepairIds checks FRAGILE before SCRAPPY (shared/engine/battleResolve.ts),
    // so FRAGILE wins and the free repair is denied. Asserted rather than
    // assumed, because §6.1 reasons about exactly this hull.
    const both = zoneEntry({
      name: 'Buccaneer', keywords: [KEYWORDS.FRAGILE, KEYWORDS.SCRAPPY],
    })
    expect(autoRepairIds([{ entry: both, side: 'a' as const }], { [both.instanceId]: 85 }))
      .toEqual([])
  })
})
```

85 is inside the repair band on both sides: `REPAIR_WINDOW_MIN_PERCENT` is 80
and `SURVIVE_HP_PERCENT` is 90, so a hull at 85 is the only case in which the
FRAGILE/SCRAPPY ordering can be observed at all.

## Deploy note

Merging to `main` deploys automatically via the Supabase GitHub integration,
which runs migrate → seed → deploy. This wave adds **no migration** — every card
change is a column value or a jsonb key on an existing row, so the seed step
alone applies it. `game-action` must show an incremented version afterwards;
verify **by content, not file count** (a deploy legitimately reads back with
fewer modules, because type-only imports are erased in transpilation).

⚠ **The two effect edits reach games already in progress — and so does the card
data, wherever an effect mints straight from the catalog.** A Marauder dealt
before this deploy carries a frozen snapshot that still names `marauderOnPlay`
and still prints "reduce its cost by 50k" — and the moment `game-action`
redeploys, that Marauder stops discounting while its text goes on promising it.
The asymmetry runs the other way on price: an in-flight Marauder keeps its 40k
snapshot, so it is *cheaper* than one dealt after the seed step, having lost the
discount either way. Plunderer likewise begins surcharging mid-game.

The card data is not actually frozen for in-flight games either:
`supabase/functions/game-action/index.ts` (around lines 124-126) loads the
**live** `cards` table into `ctx.catalog` on every action that needs one, so a
catalog-minting effect (`{ needsCatalog: true }`) always mints the row as it
stands today, never the frozen snapshot a player's hand or deck remembers. The
moment this deploys, `spawnBuccaneerEffect` starts minting a 225k Buccaneer hull
when a player plays their frozen Spawn Buccaneer card — the one still priced at
150k in their hand — and `reservesEffect` hands a player a Loggerhead without
`halfCost` and a Tarpon with `subScreen`, alongside deck copies dealt before the
deploy that still carry the old values.

The only thing that stays frozen is a card's OWN snapshot — the specific copy
already sitting in a hand, deck, or on the board, never re-read once dealt.
Keeping the registry ids is what spec §6.1 requires, and the only way to spare
in-flight games would be a new id — which orphans the old implementation and is
the first half of the Kraken/Paddlegun failure. Say so in the PR body rather
than discovering it in a player report; 28 games were in flight at the time of
writing.
